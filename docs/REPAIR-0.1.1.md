# 0.1.1 接入修复

## 已确认的原因

1. rc.5 的非 insert patch 中，`name` 是目标行的名称校验条件，不能用于重命名。
   0.1.0 写成 `id: compaction-basic` 加 `name: dsh-context-recall/compaction`，
   实际被 composer 以 `name mismatch` 跳过。
2. Web 的根层 `compaction-basic` 默认禁用；实际压缩引擎在四个 Agent preset 的隔离组中。
   即使替换根层实例，也不会覆盖会话所使用的后端。
3. 0.1.0 改写了共享 `session-query-sqlite` 的配置。SessionController 依赖该服务，
   因此安装过程会触发核心依赖的热加载重建。现场确认它停留在 `failed`，实际会话 API
   返回 `gateway/service-unavailable`。第二次点击无弹窗不代表恢复：启用选择先保存，
   热加载失败不会回滚选择，再次设置相同标志也不保证重试失败服务。

首次弹窗的原始异常栈未保存在可读取的日志或状态 API 中。隔离测试反复重建原生查询服务
可以成功，因此没有把资源泄漏或某个未证实的内部异常认定为该次失败的确定原因。

## 修复方式

- 通过公开的 `agentPresets.serviceFor(agent, 'compaction')` 找到实际后端，只装饰该实例的
  `summarize` 扩展点；保留原生事务、策略、隔离及原型，不重写 LLM 路由。
- 覆盖现有及新建会话，后端热加载后重新绑定，停用时恢复实例原有方法。
- 在插件私有的 Cordis 隔离组里运行官方全文查询服务，不再改写核心查询配置。
- GUI 配置及凭据持久路径不变，0.1.0 的已保存配置继续读取。

## 补上的验证

旧测试验证了摘要子类与独立服务调用，却没有验证真正发布的 bundle 和 Web preset 组合，
遗漏了上述两个接入问题。新版使用固定 rc.5 包中的完整 base/web YAML 做组合验证，
并实际加载隔离预设中的原生压缩引擎、执行摘要事务、启停私有索引组及请求真实 HTTP 会话接口。
这轮测试使用临时实例和合成数据，不会调用生产模型或修改日常实例。

修复版准备完成不等于日常实例已经升级。按部署约定，用户确认安装 0.1.1 后，
再核对实时 `active` 状态与会话接口，必要时单独确认运行实例的恢复操作。
