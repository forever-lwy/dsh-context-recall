# 会话列表与新建故障恢复

现场版本：dsh `0.2.1-rc.5`，插件 `0.1.1`。日期：2026-11-01。

## 现场证据

- 原有 6 个持久会话日志均存在，逐帧解压及 JSON 校验通过：94 帧、215 条记录，没有解析错误。
- 回忆插件处于 active，但原生 `session-controller` 仍是此前遗留的 failed。
  `session/modelCatalog` 返回 `gateway/service-unavailable`，会话列表与新建均依赖同一控制器。
- 官方管理接口单独重试控制器后，取得确定的原生异常：

  ```text
  file-upload: Agent resolver is already registered
  ```

## 已复现的根因

rc.5 的 `FileUploads.registerAgentResolver()` 把解析器回调存入服务字段，清理时用
`this.agentResolver === resolve` 判断该回调是否仍由自己持有。Cordis 会为服务直接字段上的
函数生成 tracing proxy，字段读取值与闭包里的原函数因此不相等，旧回调未被清除。
随后 SessionController 重建时发现旧解析器仍存在，构造失败。

这个失效状态不会因回忆插件停用或 0.1.1 安装成功自动消失。此前验收仅证明新包构建与
独立上下文的行为，没有实际恢复日常实例中已经失败的核心服务，是线上恢复步骤的遗漏。
旧隔离测试借用了真实方法，却把上传服务替换成普通对象，也未覆盖真实 Service 的 tracing 行为。

## 本次已执行的恢复

用户明确要求恢复当前故障后，通过官方插件管理接口重新加载 `include:file-upload`。
这个服务恢复为新实例后，依赖它的 SessionController 自动恢复，连带 schedule 与
ui-deliverables 均回到 active。没有修改已安装模块、升级插件或重启容器。

相关 profile 配置与 package.json 在恢复操作结束后逐字节核对，与操作前一致。
临时上传收据随服务重载重置；持久会话日志没有还原、移动或删除。

## 恢复验收

- 原来 6 个会话全部重新可见，用户界面后来新增的一个空白会话也正常出现。
- `session/modelCatalog` 和 `session/list` 均成功。
- `session/create` 实际调用成功，复用已有空白会话，未制造额外测试会话，未发送模型请求。
- 当前启用的插件条目均为 active；回忆插件保持启用。
- 新增真实 `FileUploads`、SessionController、AgentLoop 和 JSONL 持久化的故障恢复测试，
  验证重复注册故障、插件启停不能修复遗留失败、正确重载顺序、历史列表、新建及原文不变。

本次是运行状态恢复，插件业务代码没有变化，现有 0.1.1 版本包不需要重装或替换。
